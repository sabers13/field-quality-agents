# Q8: issue and report agents, end-to-end wiring

## What

- **Issue agent** (`src/field_quality_agents/agents/issue.py`). After each
  simulated day it rechecks every vehicle/group key that has a report in the
  last 28 days, calls Q2's `cluster_stats` and opens one issue per key while
  the Poisson spike holds and at least two replay cases support it. It links
  the matching recalls and investigations and drafts 8D D1–D4 and a one-page
  decision memo. D1 is placeholder roles; D2, D3, D4 and every memo paragraph
  name case, recall or investigation ids.
  `checked_citations` validates every citation in code against a source index
  (id must resolve; any quoted span must be found after whitespace
  normalisation), and `_ensure_cited` rejects an uncited statement before an
  issue is returned. Issue ids are deterministic
  (`I-<yyyymmdd>-<sequence>`), and open keys are not reopened.
- **Report agent** (`src/field_quality_agents/agents/report.py`). Builds the
  weekly report from the run's own `CaseRun`, `Proposal` and `Issue` records:
  reports received, decisions in the week, cases still needing an engineer,
  open issues, targeted-test proposals and the week's `Metrics`. Every number
  in the narrative is counted from those tables; nothing is estimated.
- **Prompts** `prompts/issue/p1.md` and `prompts/report/p1.md` are versioned
  JSON-output prompts for a later model-drafted variant. The shipped agents are
  deterministic so citations and numbers cannot drift.
- **Run pipeline** (`src/field_quality_agents/run/`):
  - `pipeline.py` plays cases in received-date order, day by day, calls the
    issue agent after each day and the report agent after each week, then writes
    the run directory and the final before/after metrics.
  - `data.py` reads the committed parquet files, a fixture DuckDB, or a
    temporary DuckDB built from fixture SQL.
  - `tools.py` adapts Q2's tools to Q5's `ToolRegistry` and captures exact
    per-case evidence; `ReplayTools` serves the recorded tool results back to a
    live replay.
  - `metrics.py` computes PLAN §7 after-metrics with the shared Q3 functions and
    pairs them with `results/baseline/metrics.json`.
  - `writer.py` writes `manifest.json`, `input_cases.json`, `cases.json`,
    `traces.json`, `extractions.json`, `proposals.json`, `decisions.json`,
    `evidence.json`, `tool_outputs.json`, `issues.json`, `eight_d.json`,
    `memos.json`, `report.json`, `reports.json`, `metrics.json`, `events.json`
    and `comparison_examples.json`, sorted and newline-terminated.
  - `dashboard.py` writes the Q10-shaped dashboard data under
    `dist/field-quality-agents/data/`.
  - `live.py` builds `fqa serve --mode live` over a recorded run: it starts the
    desk graph from `input_cases.json` with the recorded tool outputs and model
    turns, so the dashboard's approve/override/ask buttons resume real
    checkpoints and a case visibly moves.
- **CLI**: `fqa run --mode replay|record --set replay_2025 --run-id <id>` with
  `--recordings-dir`, `--data-dir`, `--db`, `--fixture-sql`, `--results-dir`
  and `--baseline-dir`. `fqa export` writes dashboard data. `fqa issues` and
  `fqa report` inspect a recorded run. `fqa serve --mode live` adds the live
  route.
- **Determinism**: a simulated day clock (`use_clock`) fixes trace, proposal,
  decision and issue timestamps; `json.dumps(..., sort_keys=True)` in intake and
  analysis makes recorded model messages order-stable; the manifest records a
  digest of the recording set. `make all` rebuilds results byte-identically.
- **Fixtures**: `tests/fixtures/e2e/replay_2025.sql` is sixteen synthetic
  reports over three June 2025 weeks, a small knowledge base, one real-looking
  spike (6 reports against threshold 5), a matching recall and investigation.
  `tests/fixtures/recordings/` holds the replay turns generated by
  `tests/e2e/generate_fixture_recordings.py` with a deterministic scripted
  model. No real model was called and no secret was used.
- **Makefile**: `all = data-check → baseline → run replay → export dashboard
  data → web build`; `e2e` regenerates the fixture run and drives Playwright.
  `scripts/check_data.py` is the cheap data check.

`tests/e2e/test_run.py` covers:

- two replays are byte-identical;
- every documented artifact is written, events are contiguous, every decided
  case has a simulated-engineer decision;
- issue and report numbers match the run tables;
- every 8D and memo citation passes `citation_validity` and every statement
  cites a real id;
- a replay miss raises `ReplayMissError`.

`tests/e2e/approve.spec.ts` drives the built dashboard over the real live API:
open case `C-2025-0002`, read its trace, approve the proposal, see the case in
the Decided column, then open issue `I-20250609-001` and read its 8D and memo.

Also verified by hand: `fqa serve` replay mode answers `/api/health` and serves
the built dashboard; `fqa issues` and `fqa report` print the recorded run.

## Deviations and shared-file changes

- **Deterministic agents, not model-drafted.** PLAN §4 does not require a model
  for issue/report drafting; deterministic code is the stronger choice for
  citation validity and for "every number from the run's tables". The versioned
  prompts are in place for a later model-drafted variant.
- **`agents/analysis.py` + `agents/intake.py`**: prompt messages are now
  serialised with `sort_keys=True`. Without this, a live replay produced the
  same JSON in a different key order and missed its recording. This is a small
  determinism fix in Q5 files.
- **`agents/state.py`**: `utcnow()` has a context-local simulated clock
  (`use_clock`). Live mode and tests keep the wall clock.
- **`agents/prompts.py`**: `AGENTS` now includes `issue` and `report`, so
  `load_prompt` validates their files with the same rules.
- **`api/live.py`**: a live case that is interrupted at a human checkpoint is
  shown as `needs_engineer` rather than the graph's intermediate `analysis`
  status. The dashboard's approve/ask controls depend on that status.
- **`api/store.py`**: docstring now documents `input_cases.json` (received
  cases, used to start live threads) and `tool_outputs.json` (full tool rows
  for a faithful live replay). The reader ignores files it does not know.
- **`.gitignore`**: `results/runs/e2e-fixture/` is regenerated by `make e2e`.
- **`tests/test_cli.py`**: updated because `issues` and `report` now inspect a
  run instead of printing a Q8 stub.
- No contract, PLAN, interface-signature, web, or design changes.
- No remote, no push, no PR, no secret, no real name.

## Open issues

- **Q9 recording switch**: `fqa run --mode replay` uses `recordings/` when it
  contains turns, otherwise the fixture recordings and fixture SQL. Once Q9
  records the real run, `make all` will replay the real set automatically; Q9
  should confirm the first real replay and may want an explicit flag.
- **Q10**: the frontend still reads its bundled Q6 fixtures in static mode.
  Q8 writes the documented `dist/field-quality-agents/data/` files; Q10 owns
  wiring `StaticDataSource` to them and the final portfolio export.
- **Live mode scope**: `fqa serve --mode live` starts up to `--live-limit` case
  threads (default 25) from a recorded run. It is an end-to-end inspection
  surface, not the Q9/Q14 production run driver.
- **LangGraph checkpoint warnings**: the contract models are not in the msgpack
  allow-list, so LangGraph prints a deserialisation warning on every checkpoint
  read. It does not change behaviour; Q9 can register the types.
- **Issue evidence grows after opening**: an open issue keeps the linked cases
  known when it opened. Later reports in the same cluster are shown by the
  cluster series but are not appended to `linked_case_ids`; that keeps a cited
  8D and memo stable.
