# Q7: backend API

## What

The FastAPI backend for the dashboard, in `src/field_quality_agents/api/`.

- **`create_app(store=..., graph=..., mode="replay", static_dir=..., heartbeat_seconds=15)`**
  builds the app. `store` is the recorded read model; `graph` is only used in
  live mode. The last two keyword arguments are additive (the frozen signature
  has `store`, `graph`, `mode`); they exist so tests and `fqa serve` can point
  at a temp build and speed up the heartbeat.
- **Cases**: `GET /api/cases` with `status`, `group`, `safety`, `q`, `limit`,
  `offset`; deterministic newest-first order with the id as the tie-break.
  `GET /api/cases/{id}` returns `CaseDetail` with extraction, proposal, trace,
  decision, similar cases, recalls and investigations. `GET
  /api/cases/{id}/trace` returns the ordered steps.
- **Decisions**: `POST /api/cases/{id}/decision` accepts `approve`, `override`,
  `ask` and `request_info`. Replay/static mode returns 409. In live mode,
  approve and override build a `HumanDecision(actor="live_engineer")` and
  resume the LangGraph checkpoint with `Command(resume=...)`. Ask and
  request-info append a human step, leave the case at `needs_engineer` and keep
  the interrupt, so a later approve still works; those overlay steps are merged
  in front of the resumed decision step and renumbered.
- **Issues**: `GET /api/issues?status=` and `GET /api/issues/{id}` with weekly
  counts, linked ids, 8D draft and decision memo.
- **KPIs**: `GET /api/kpis?window=30d` returns the seven PLAN §6 tiles computed
  from the store (cases in, prepared without edits, human touches, time to
  decision, open issues, cost per case, standard test without evidence), an
  eight-week sparkline, the newest-first feed and the before/after headline.
  The window ends at the latest recorded case date, so replaying an old run is
  deterministic; `window` is validated as `<days>d`, 1–365.
- **Comparison**: `GET /api/comparison` returns both `Metrics` objects, every
  PLAN §7 row from `metrics.compare` and the fixed four-pair headline plus the
  recorded showcase examples.
- **Weekly report**: `GET /api/reports/weekly?week_start=` returns the latest
  recorded week or the named one.
- **Replay**: `GET /api/replay/runs` and `GET
  /api/replay/runs/{id}/events?after=` serve recorded runs and ordered events.
- **SSE**: `GET /api/events` keeps a retained window per app, honours
  `Last-Event-ID` (or `?after=`), emits `retry: 3000`, replays retained events
  at or below the subscription point, then streams new events and a heartbeat
  every 15 s. Event names and data match `docs/INTERFACES.md`:
  `heartbeat`, `case_status`, `trace`, `issue`, `run`.
- **Static**: `/` serves `web/dist/index.html`; other paths serve a file when it
  exists and otherwise fall back to `index.html`. Unknown `/api/*` paths stay
  JSON 404s, path traversal is rejected, and a missing build returns a 404 that
  names `make web-build`.
- **CORS**: only `http://localhost:5173` and `http://127.0.0.1:5173` (Vite dev
  server) are allowed; the built dashboard is same-origin.
- **`fqa serve`** now runs replay mode with `--results-dir`, `--run-id`,
  `--static-dir`, `--host` and `--port`.

### Store and reader (handoff to Q8)

`ResultStore` is a protocol with `MemoryResultStore` for tests and
`FileResultStore` for production. `FileResultStore` picks the newest run or a
named one under `results/runs/` and reads a tolerant, documented layout
(docstring in `api/store.py`): `manifest.json`, `cases.json`, `traces.json`,
`extractions.json`, `proposals.json`, `decisions.json` (list or map),
`evidence.json`, `issues.json`, `eight_d.json`, `memos.json`, `report.json`,
`reports.json`, `metrics.json` (`{"before", "after"}`), `events.json` and
`comparison_examples.json`. Missing files mean "no data"; malformed JSON raises
`ResultStoreError`.

## How tested

`tests/api/` (51 tests), all offline against `MemoryResultStore` and a
`FakeGraph` with `invoke`/`get_state` and a resumable checkpoint:

- `test_cases.py`: list ordering, every filter, search, paging, item counts,
  detail with evidence and decision, 404s and trace order.
- `test_live_decisions.py`: approve resumes and decides, override carries the
  edited proposal, ask leaves the case with an engineer and a later approve
  still works, replay 409, live-without-graph 409, unknown case 404, finished
  checkpoint 409, wrong-case edited proposal 400, body validation.
- `test_reports.py`: issue list/detail/filter, seven KPI ids and values, window
  changes and validation, feed order and event mapping, comparison rows and
  headline, 404 without metrics, weekly latest/by-week/404.
- `test_replay.py`: run order, event order, `after`, unknown run and bad
  parameter.
- `test_events.py`: retry line and heartbeat, `Last-Event-ID` replay, decision
  publishes `case_status` and `trace`; the stream is closed after the first
  heartbeat.
- `test_static.py`: index, asset, SPA fallback, traversal rejection, `/api/*`
  stays a JSON 404, missing build message.
- `test_store.py`: every documented file is read, newest/named run selection,
  missing root, malformed JSON error, and the app served from a file-backed run.

## Deviations and shared-file changes

- **`pyproject.toml` + `uv.lock`**: added `fastapi>=0.115` and
  `uvicorn>=0.30`, which the scaffold did not include even though Q7's brief
  needs a FastAPI app and `make serve`. This is the only shared-file change.
- **`create_app` additive keywords**: `static_dir` and `heartbeat_seconds` are
  extra keyword-only arguments with defaults. The three frozen arguments are
  unchanged.
- **`GraphLike` protocol**: the graph is typed structurally (`invoke` and
  `get_state`) so tests can pass a fake; the annotation uses `Any` for LangGraph
  compatibility. It is satisfied by a real `CompiledStateGraph`.
- **Ask semantics**: the frozen Q5 graph treats a resumed decision as terminal,
  so `ask`/`request_info` are recorded as overlay steps and the interrupt is
  kept rather than resuming the graph. This is what makes a later approve
  possible; the response returns `pending: null` because no decision is
  pending.
- **Feed mapping**: recorded event kinds are translated to the SSE names
  (`case`/`decision` → `case_status`, `report` → `run`, `trace`/`issue`
  unchanged) because the command centre feed is typed with the SSE names.
- **KPI reference date**: the window ends at the newest recorded case rather
  than wall-clock time. Without this, an old replay would show zero cases in
  every window.
- No PLAN, contract, design, Makefile or dashboard-file edits.

## Open issues

- **Q8 wiring**: `fqa serve` is replay-only. Q8/Q9 must build the desk graph,
  construct `LiveDesk` (or pass `graph=` to `create_app`) and expose a live
  serve mode; the decision route, `EventBus` and ask/override behaviour are
  ready.
- **Q8 writer contract**: Q8's run directory must write `events.json` for the
  replay page and feed, and should write `extractions.json` and `evidence.json`
  so case detail is complete. The exact layout is in `api/store.py`.
- **Live issue events**: the bus supports `issue` and `run` events, but only
  Q7's decision route publishes today; Q8's issue agent should publish to
  `app.state.bus`.
- **Durability of ask overlays**: ask/request-info steps live in the process's
  `LiveDesk`. A server restart loses those visible steps (the graph checkpoint
  still holds the pre-ask state). Q9 should decide whether live asks need a
  checkpoint- or disk-backed store.
- **CORS** is limited to the Vite dev origins. A different dev host or port
  would need an explicit addition.
- KPI tiles derived from a window (time to decision, NTF-without-evidence) use
  the recorded window cases, while the share metrics in the comparison come
  from the whole run, as they are recorded.
